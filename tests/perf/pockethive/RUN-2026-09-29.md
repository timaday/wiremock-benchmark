# PocketHive WireMock comparison — completed September 30, 2026

Both WireMock runtimes passed the short throughput and integrity benchmark through
PocketHive. Each completed all 91,800 load requests and reconciled all 275,400
capture events, plus a separate 48-request smoke. This does not establish one-hour
memory stability or low PocketHive resource overhead.

Rates and resource samples use a common 60-second interval, starting 20 seconds
after the latest lane's first offered request. Every lane offered through the
window. Latency percentiles cover all 91,800 requests. Collection rates can exceed
offered rates within this window because previously queued results drain during
it; they are not a higher sustained injection rate.

HTTP timing is the processor's response-header duration, excluding body reads.
Pipeline timing runs from request construction to evidence-worker processing and
includes queueing, body reads and result processing. Neither is an independently
measured Gatling-equivalent full HTTP latency. The pipeline's additional delay
must be considered when using this scenario for latency benchmarking.

WireMock resource samples came from its capture metrics, container statistics and
GC logs: 15 official samples and 14 headless samples within the measurement
windows. Container memory is Docker's reported usage, not a separately measured
RSS. The host was shared and already using swap. PocketHive MCP exposes lifecycle
and diagnostic projections but no per-worker CPU/heap time series in this tool
catalogue; those were not measured through an unauthorized alternate path. The
four load processors each configure 1,800 platform threads and a 1 GiB maximum
heap. This run establishes load delivery, not a lightweight generator comparison.
The two runtime/JVM combinations were measured sequentially once; the differences
cannot be attributed solely to the headless wrapper.

## Workload and evidence

- PocketHive public ingress: `http://localhost:8088`, MCP release `0.15.35`.
- Published bundle source: `d581092dd83a822950c8a15e4e97ae4924c0af16`.
- Four generator/processor lanes, each offering 255 requests/s for 90 seconds;
  finite non-rotating CSV inputs, followed by complete draining.
- Six-second delay; 1/5/10/50 KiB exact request and response bodies; static, JSON
  and text templates from the sibling `wiremock-benchmark/tools/fixtures.py`.
- WireMock `3.13.2` in both cases, capture enabled, 4 CPU / 4 GiB container limit,
  3 GiB maximum JVM heap; Java `17.0.19+10` and `27+35-2325` respectively.
- Explicit Artemis work transport; one evidence moderator writes compact results
  to a dedicated persistent Redis list per run.
- All expected IDs, actual request/response hashes, HTTP statuses, capture phases
  and archive hashes verified. Final capture pending/errors were zero, and every
  committed event was confirmed. Both Redis result lists drained completely.

## Validation and startup corrections

Initial controller creation failed before any requests. The first bundle lacked
explicit Rabbit settings; a bounded controller log read, approved by the user,
identified that validation error. The second attempt also created no workers.
Inspection of the selected deployment showed that it uses Artemis. The corrected
bundles explicitly use Artemis and a separate Redis evidence sink. All four
replacement publications succeeded, and all nine workers became healthy in each
subsequent swarm. Failed empty swarms were removed through MCP.

Release 0.15.35 offline validation accepted all 36 worker declarations and passed
12 payload-template checks. Live smoke then checked all 48 requests per runtime.
`test_analyze.py` passed five mutation checks against the retained official smoke:
missing ID, duplicate ID, corrupt response hash, HTTP error and undrained captures
were each rejected. Python compilation and `git diff --check` passed.

These are local development observations. HiveGate was unavailable; they are not
governed HiveGate execution or endurance-test evidence.

Review: no blocking findings in the benchmark-only changes. The repository-wide
owner search found `analyze.py` as the sole owner of this PocketHive evidence
verdict; canonical response bytes remain owned by the sibling fixture catalogue.
The corrected generator produced a fresh smoke bundle accepted by the deployed
release parser (nine worker declarations). The benchmark changes are ready to
review; service behavior, public contracts and global configuration were not
changed. Per-worker resource measurements and an endurance run remain unverified.
